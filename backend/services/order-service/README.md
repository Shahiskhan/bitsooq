# Order service

Standalone Java 25 / Maven application. Build with `mvn verify`; it does not depend on any sibling project. The service owns `orders`, `order_items`, `inbox` and `outbox` in its own MySQL instance.

`POST /api/orders` requires an authenticated gateway request and `Idempotency-Key` (1–128 characters: letters, digits, `.`, `_`, `:`, `-`). Body accepts `items` plus an optional `shippingAddress`, `deliveryRateId`, and `paymentMethod` (`MOYASAR`, `CRYPTO_USDT_ETH`, or `CASH_ON_DELIVERY`). A supplied address includes recipient name, phone, street, optional apartment/area/postal code/instructions/GPS pin, city, region, and ISO country code; an address requires a valid delivery-rate ID returned for that destination. Up to 20 distinct SKUs, quantities 1–1000; SKUs contain 1–64 uppercase letters, digits, `_` or `-`, matching the inventory contract. Prices are deliberately absent. The product service reserves inventory and calculates the authoritative USD amount in integer minor units. A successful POST returns 202 with `orderId` and asynchronous status. Reusing a key for a different request returns 409. `GET /api/orders/{id}` returns only an order owned by the signed user, including its address snapshot and shipment/tracking activity.

Transitions: PENDING → RESERVED → CONFIRMED, or PENDING/RESERVED → CANCELLED following inventory rejection/payment failure. Terminal states do not regress. No customer cancellation endpoint is exposed, because cancellation after payment authorization requires a separate refund saga. The reservation/payment deadline is 15 minutes by default. There is no automatic destructive timeout after payment may have succeeded: quarantined or stuck workflows require reconciliation before compensation.

Each domain mutation and outgoing event commits in one local SQL transaction. The outbox publisher acknowledges Kafka before marking a record published. A crash between those steps produces a duplicate; every consumer must use its transactional inbox. Outbox publication uses bounded Kafka waits and row locks with `SKIP LOCKED`. A poison event is quarantined in `commerce.saga.v1.order-service.DLT` after bounded retries; operators must reconcile/replay it. Quarantine is not a business cancellation.

All API calls require the gateway's signed internal headers. The HMAC input is `method + "\n" + rawPath + "\n" + userId + "\n" + roles + "\n" + epochSeconds + "\n" + requestId`. The SHA-256 signature is unpadded Base64URL. Receivers reject duplicate headers and clock skew beyond 30 seconds. Keep the HMAC key in a secret manager, synchronize clocks, and require mTLS/network policy in production; HMAC headers alone do not encrypt traffic or prevent a captured request being replayed within the skew window. The durable order idempotency key protects repeated placement.

Required environment: `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `CONFIG_SERVER_URL`, `CONFIG_USERNAME`, `CONFIG_PASSWORD`, `EUREKA_URL`, `KAFKA_BOOTSTRAP_SERVERS`, `INTERNAL_HMAC_SECRET`. Port 8083. Only `/actuator/health` and its probes are publicly readable within the private network.

Tests exercise canonical request retry, conflicting key reuse, ownership, authoritative pricing, duplicate events, terminal-state immutability, transactional inbox rollback, and signed-header rejection. H2 tests do not establish MySQL locking behavior or Kafka delivery guarantees; run integration and failure-injection tests against the actual infrastructure before deployment.

## Customer history and admin queries

GET /api/orders?after=CURSOR&size=20 returns the signed customer's own keyset page {items,nextCursor}; items contain orderId,userId,status,totalMinor,currency,createdAt. Omit after for the first page. Cursor values are opaque Base64url time/UUID tuples.

STAFF/SUPER_ADMIN can call GET /api/admin/orders with optional status and GET /api/admin/orders/{id}. The latter includes immutable items and owner metadata. SUPER_ADMIN alone may call GET /api/admin/analytics/orders for own-database counts and confirmed USD revenue; these are order-domain metrics, not a cross-service financial ledger. The initial aggregate scans order status groups, so move high-volume analytics to an event-fed read model before large-scale analytical workloads. V2 adds user/time and status/time indexes without altering V1.

## Delivery, shipments, and cash on delivery

`POST /api/delivery/options?currency=USD` matches country, region, city, optional area, and postal prefix to active delivery zones and returns available fees, ETA windows, and COD eligibility. STAFF/SUPER_ADMIN can create zones at `POST /api/admin/delivery/zones`, service rates at `POST /api/admin/delivery/zones/{zoneId}/rates`, and pause/resume either with `PATCH /api/admin/delivery/zones/{id}/active` or `PATCH /api/admin/delivery/rates/{id}/active`; the dashboard exposes these controls. Rates are currently USD minor units and no shipping coverage is seeded in MySQL, so staff must configure coverage before live checkout can proceed.

When inventory is reserved, a COD order moves to CONFIRMED with `payment_status=COD_DUE`; an eligible shipment is created with an estimated delivery timestamp. Staff can record exact-amount cash collection at `POST /api/admin/orders/{id}/cod-collection` using an `Idempotency-Key` and collection reference. Staff update a shipment with `PATCH /api/admin/shipments/{id}` and can provide status, carrier, tracking number/URL, event description, and event location. Customer order reads return shipment events and ETA. These endpoints do not call a carrier, book delivery, purchase labels, or reconcile courier cash remittance. Return/refund request APIs remain unimplemented.

Gateway authentication is enforced again through the signed context filter; admin controllers additionally check trusted roles. Outbox batching has a single20-second deadline and25-second transaction timeout.
